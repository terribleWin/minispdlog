# 设计决策

本文记录 minispdlog 当前代码中的关键取舍。它不是愿望清单；尚未落地的想法应进入 issue 或路线规划，而不应写成现有能力。

## 设计目标

- 同步直写与异步解耦都保持一等公民；
- 数据路径足够小，能够从调用点追踪到最终输出；
- 过载、刷新、持久性和平台限制都有显式配置与可测试语义；
- 文本、JSON 与不同输出目标通过 formatter / Sink 组合，而不是复制 logger 体系；
- 公开 API 采用 C++20，内部实现保持独立可读。

非目标包括：与 spdlog 的 ABI/API 完全兼容、隐藏所有平台差异、实现通用遥测 SDK、承诺任意硬件上的固定性能。

## ADR-001：保留同步与异步两条路径

同步 `logger` 直接进入 Sink，异步 `async_logger` 只重写热路径，把拥有数据的消息投递到线程池；工作线程使用 `backend_sink_it_()`，不会再次入队。短正文使用消息内联空间，生产者线程按配置版本缓存线程池共享快照，稳定运行时不为每条日志争用共享引用计数。

结果是两条路径共用级别、formatter、Sink 和 registry。用户可以按 logger 选择模式，不需要给整个进程做一次不可逆开关。代价是文档必须分别说明调用返回、刷新和退出语义。

## ADR-002：异步队列有界且策略显式

默认后端是互斥锁 + 条件变量的 MPMC，支持多个消费者；可选后端是单消费者 MPSC 环。两者都要求非零容量，并暴露 `block`、`discard_new`，MPMC 额外支持 `overrun_oldest`。

有界队列让内存上限和过载行为可讨论。库不替应用选择“延迟还是丢失”，而是公开策略与池级计数。`overrun_oldest` 只覆盖日志消息，不覆盖刷新或终止控制消息；控制消息位于队首时，新日志会被拒绝并计入丢弃数。无锁后端只允许一个工作线程，以保持队列算法的消费模型。

## ADR-003：参数展开与行格式化分层

`logger::log()` 在调用线程使用 fmt 把参数展开为 payload，并捕获时间、线程、进程和源码位置。异步消息复制 payload，短正文保存在 256 字节内联缓冲区中；最终 `pattern_formatter` / `json_formatter` 在 Sink 所在线程运行。

这样不会把调用栈中参数引用悬挂到后台线程，同时允许不同 Sink 对同一记录生成不同表示。代价是异步调用并不免除 payload 格式化成本。

## ADR-004：Sink 拥有独立 formatter

每个 `base_sink` 默认拥有一个 `pattern_formatter` 和复用缓冲区。`logger::set_formatter()` 为多个 Sink 克隆 formatter，避免共享带缓存的 formatter 状态。

JSON wrapper 默认维持 `json_formatter`，防止通用 `set_pattern()` 意外破坏采集 schema；确有需要时必须显式 `allow_custom_formatting(true)`。

## ADR-005：logger 的 Sink 列表采用写时复制

记录路径以原子方式加载 `shared_ptr` 快照，不在 Sink I/O 期间持有列表变更锁。添加和移除 Sink 时复制 vector 并发布新快照。

这一选择优化的是“记录频繁、拓扑变更少”的常见比例。动态变更不是零成本，但旧快照能安全完成正在进行的日志调用。

## ADR-006：批量文件使用双缓冲、sidecar WAL 与行恢复

前台缓冲达到阈值后与冻结缓冲交换；`_mt` Sink 在实际写冻结批次时释放 Sink 锁。启用恢复时，先写包含目标偏移的 WAL，再写主文件并删除 WAL。重新打开时回放 WAL，并按换行修复 256 KiB 尾部窗口。

这是面向追加式日志的恢复协议，不是数据库事务。它依赖每条格式化记录以换行结束，且 durability 由调用方选择。大小滚动与按日切分目前没有复用该 writer，文档不得把恢复保证泛化到所有文件 Sink。

## ADR-007：JSON 使用稳定核心字段 + 静态资源字段

`json_formatter` 固定输出时间、级别、logger、正文、线程和进程字段，可附加 string/int/bool/null 类型的静态资源字段。核心字段名保留，资源冲突被忽略。

这保持 schema 简单、可直接按行采集，也使 formatter 可克隆。当前不在单次日志 API 中引入任意动态键值或上下文传播；需要这些能力时应先设计生命周期、类型和并发模型。

## ADR-008：运行拓扑显式，不隐藏平台限制

Linux 网络 Sink 使用真实 UDP/TCP Socket；其他平台构造时明确失败。Qt Sink 只有找到 Qt Widgets 后才编译，且不拥有 `QObject`。核心库不为了统一表面接口而模拟成功。

调用方可以通过 `network_sink_supported()` 和构建选项建立自己的降级路径。

## ADR-009：registry 管理发现，不垄断所有权

工厂创建 `shared_ptr<logger>` 并注册具名实例。registry 的映射操作持锁，`flush_all()` 则先取得快照再在锁外 I/O，避免回调重入映射锁。

logger 仍可不注册而由业务直接持有。名称唯一性在注册时验证；`shutdown()` 是全局异步生命周期边界，会刷新、停止线程池并清空 registry。

## ADR-010：性能结论必须拆分测量

库提供无外部依赖的性能烟雾测量，以及 `null_sink`、队列微基准和异步基准，用于区分过滤、formatter、入队与 I/O。仓库不提交脱离测量环境的“更快”结论，也不把异步入队时间冒充端到端交付时间。

性能修改必须先保持测试语义，再用可复现实验说明瓶颈变化。方法见[性能验证](performance.md)。

## 扩展检查表

新增 formatter 或 Sink 前回答：

1. 谁拥有外部资源，析构和 `flush()` 分别保证什么？
2. `_mt` 与 `_st` 的并发契约是什么？
3. 异步消息中的所有数据在工作线程执行时是否仍有效？
4. 错误是抛出、计数还是丢弃，用户能否观察？
5. 是否保持一条记录一个换行，若否会怎样影响网络 framing 和恢复？
6. 哪些平台真正实现，哪些配置需要显式失败？
7. 单元测试、故障测试和基准分别验证什么？

与外部项目的边界见[与 spdlog 的设计边界](design-vs-spdlog.md)，对象关系见 [`architecture.puml`](architecture.puml)。
